# ZAGS UI Tests

Учебный проект для Романа и Даниила: Python, Selenium, Pytest и Page Object.
Smoke-тесты открывают форму администратора, проверяют пустые поля и ввод/очистку фамилии
на латинице и кириллице. Сценарии собираются из импортируемых шагов с параметрами.
Smoke-тесты администратора не создают и не удаляют записи на стенде.
В `tests/ui/test_user.py` добавлен сценарий регистрации брака: он отправляет заявку.
Для безопасного знакомства с отчетом запускать только `tests/ui/test_admin.py`.

## Быстрый старт на Windows

Нужны Python 3.11+, Chrome или Edge, Git и VPN для доступа к стенду.
В терминале из корня проекта:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
Copy-Item .env.example .env
```

Открыть `.env` и заполнить `ZAGS_USERNAME` и `ZAGS_PASSWORD` выданными доступами
HTTP Basic Auth. Не путать с данными заявителя или режимом администратора в интерфейсе.
Значения из окружения имеют приоритет над `.env`. Пароль не выводится настройками,
но адрес авторизации существует в памяти браузера: не публиковать трассировки и адреса с ним.

Устанавливать ChromeDriver вручную обычно не нужно: Selenium Manager подбирает драйвер.
Первый запуск требует доступа к серверам загрузки. При ошибке проверить сеть,
VPN, установленный браузер и старый драйвер в PATH. Проверка сертификатов не отключается.

## Запуск

В VS Code открыть новый терминал через Terminal → New Terminal. Настройки проекта
добавляют `.venv/Scripts` в PATH только этого терминала, поэтому доступны обычные
команды `python`, `pip`, `pytest` и `ruff`. Если терминал был открыт до изменения
настроек, закрыть его кнопкой корзины и создать новый. Системный PATH не меняется.
Внешний PowerShell потребует активации окружения либо явного пути к его Python.

```powershell
# Локальные проверки фреймворка без VPN, паролей и браузера (по умолчанию).
pytest

# Реальные UI-тесты ЗАГСа: явно включаем маркер ui.
pytest tests/ui -m ui -v

# Без окна браузера, либо через Edge.
pytest tests/ui -m ui --headless
pytest tests/ui -m ui --browser edge

# Проверка стиля и сбор тестов без их исполнения.
ruff check .
pytest tests/ui -m ui --collect-only
```

Тесты рассчитаны на русский интерфейс и текущие шесть обязательных полей первого шага
администратора. Они проверяют UI, а не успешную регистрацию администратора.
Ожидания при изменении требований необходимо пересматривать, а не автоматически
подгонять под фактическое поведение. Каждый тест получает новый браузерный сеанс.

Дополнительно `--screenshot-on-failure` сохраняет PNG в `artifacts/` при падении UI-теста.
Скриншоты могут содержать данные стенда, поэтому по умолчанию выключены и исключены из Git.
Готовые отчеты JUnit можно получить стандартным `--junitxml=artifacts/results.xml`,
предварительно создав папку `artifacts`. Отчеты также не публиковать без проверки содержимого.

## API-примеры

Добавлены Requests-клиент, импортируемые шаги, общие настройки и API-фикстуры.
Четыре примера GET/Basic Auth проверены на стенде; POST создания администратора
вынесен отдельно и без `--allow-api-writes` пропускается.

```powershell
pip install -e ".[dev]"
pytest tests/api -m api -v --alluredir=allure-results --clean-alluredir
```

Обычный `pytest` теперь исключает UI и API: по умолчанию запускаются только локальные проверки.

## Allure

Подключен `allure-pytest`: понятные названия и группировка smoke-тестов,
переиспользуемые шаги и автоматический PNG при падении UI-теста с отчетом.

```powershell
pip install -e ".[dev]"
pytest tests/ui/test_admin.py -m ui -v --alluredir=allure-results --clean-alluredir
```

Для просмотра нужен отдельный Allure CLI. Установить Node.js LTS, затем:

```powershell
npm install -g allure
allure --version
allure generate allure-results --clean
allure open allure-report
```

Это команды Allure Report 3. Уже установленный Allure 2 можно использовать
с теми же результатами: `allure generate allure-results --clean -o allure-report`,
затем `allure open allure-report`; для него нужна Java.

[Пошаговая инструкция и пример](docs/allure.md) · [Домашнее задание](docs/homework_allure.md).

## Структура

```text
zags/
  settings.py              # Настройки, валидация, Basic Auth
  pages/
    base_page.py           # Общие явные ожидания и клик
    home_page.py           # Главная страница
    admin_page.py          # Форма администратора
  steps/
    navigation.py         # Шаг открытия приложения
    admin.py              # Действия и проверки формы администратора
tests/
  conftest.py              # Параметры командной строки
  ui/conftest.py           # Браузер, настройки и завершение сеанса
  ui/test_admin.py         # Независимые UI-сценарии
  unit/test_settings.py    # Локальные проверки конфигурации
.github/workflows/checks.yml
```

Три уровня: `tests` описывает порядок шагов и тестовые данные, `steps` содержит
переиспользуемые действия и проверки, `pages` работает с Selenium и локаторами.
В тестах нет CSS/XPath, вызовов WebDriver и повторяющихся проверок состояния.
Ожидаемые значения передаются из сценария в проверочный шаг, а не зашиваются в него.
Не хранить WebElement между переоткрытиями формы: DOM и генерируемые ID меняются.
Используем явные ожидания; не добавляем `sleep`, не смешиваем их с implicit wait,
не делаем автоматические повторы, скрывающие нестабильность.

## Новый тест

1. Импортировать нужные функции из `zags.steps` и составить последовательность шагов.
2. Если шага нет, добавить именованную функцию с параметрами в соответствующий модуль
   `zags/steps`. Действия и проверки именовать отдельно: `fill_...`, `open_...`, `check_...`.
3. Локаторы и низкоуровневые действия добавлять в Page Object, а не в тест или шаг.
4. В проверочных шагах использовать `assert` с фактическим и ожидаемым результатом.
5. Фикстуры создают настройки и браузер, шаги явно описывают переходы между страницами.
   Новый браузер на каждый тест сохраняет независимость сценариев.

Пример самостоятельного сценария:

```python
import pytest

from zags.steps.admin import (
    check_admin_form_closed,
    check_admin_surname,
    close_admin_form,
    fill_admin_surname,
    open_admin_form,
)
from zags.steps.navigation import open_zags


@pytest.mark.ui
def test_change_surname(driver, settings):
    home = open_zags(driver, settings)
    admin = open_admin_form(home)
    fill_admin_surname(admin, value="Training")
    check_admin_surname(admin, expected="Training")
    fill_admin_surname(admin, value="Updated")
    check_admin_surname(admin, expected="Updated")
    close_admin_form(admin)
    check_admin_form_closed(admin)
```

Шаг получает страницу явно: нет глобального драйвера, скрытого общего состояния,
исполнения строк или универсального раннера команд. Создание новых шагов не требует
изменения существующих тестов. Проверочные шаги дополнительно проверяются локально
на правильных и неправильных состояниях в `tests/unit/test_check_steps.py`.

API-клиент уже добавлен; работу с базой данных и расширение сценариев добавляем по программе:
добавляем их по мере прохождения программы, а не как пустые заготовки.

Однотипные входные данные передавать через `pytest.mark.parametrize` с понятными `id`.
Для настроек использовать `make_settings(**overrides)`: фикстура берет валидный набор
из `settings_data`, а тест меняет только нужные поля. Проверки с разной целью остаются
отдельными функциями, без универсального раннера и условных веток внутри теста.

## GitHub

Репозиторий на GitHub и коммиты этим шаблоном не создаются автоматически.

```powershell
git init
git branch -M main
git add README.md pyproject.toml .gitignore .env.example zags tests .github .vscode/settings.json
git diff --cached
git commit -m "Add ZAGS Selenium test framework"
```

Перед коммитом проверить, что нет `.env`, паролей, `.venv` и материалов учеников.
Создать пустой приватный репозиторий GitHub без README, взять его адрес и выполнить:

```powershell
git remote add origin <адрес-созданного-репозитория>
git push -u origin main
```

Команду с `<...>` не запускать буквально: заменить адрес своим.
Если это уже клонированный репозиторий, не переинициализировать его и не менять remote вслепую.
GitHub Actions запускает локальные unit-тесты и Ruff, сохраняет сырые результаты Allure
в артефакте `allure-results`. Для просмотра скачать артефакт и сгенерировать HTML локально.
Доступ к VPN и стенду на публичном runner не предполагается; UI автоматически не запускаются.

Зависимости заданы совместимыми диапазонами в `pyproject.toml`. После согласованного
обновления и проверки на обеих машинах можно сохранить точный набор через
`python -m pip freeze > requirements.lock.txt` и коммитить его. Пока lock-файла нет,
проект не обещает побайтово одинаковые версии зависимостей при установке в разные дни.
