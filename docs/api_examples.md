# API тесты ЗАГСа на Python

Примеры добавлены в существующий проект. Установка и `.env` общие с UI, браузер для API не нужен.
Нужны VPN и выданные доступы HTTP Basic Auth. Ожидаемый результат должен иметь источник:
Swagger, требования или явно согласованное наблюдение стенда. Не менять assertions автоматически под ответ.

## Обновить свою ветку

Сначала сохранить работу коммитом и проверить `git status`. Если есть незавершенный merge,
сначала завершить его. На своей рабочей ветке:

```powershell
git fetch origin
git merge origin/main
pip install -e ".[dev]"
```

При конфликте общих файлов совместить нужные изменения, а не принимать целиком все входящее.
Не заменять свои UI-сценарии чужой реализацией.

## Команды

Из корня проекта в терминале VS Code с `.venv`:

```powershell
# Unit-проверки без VPN, браузера и паролей.
pytest

# API: четыре проверки чтения и авторизации. POST пропущен.
pytest tests/api -m api -v --alluredir=allure-results --clean-alluredir

# Только два позитивных примера GET.
pytest tests/api/test_applications.py -m api -k "returns_list or existing_application" -v

# Состав тестов без исполнения.
pytest tests/api -m api --collect-only -q

allure generate allure-results --clean
allure open allure-report
```

По умолчанию обычный `pytest` исключает `ui`, `api` и `api_write`, поэтому не обращается к стенду.
Сетевые ошибки не превращаются в Passed или Skip. Единственный условный Skip позитивного чтения —
если на стенде нет ни одной заявки; этот факт виден в отчете.

## Как читать код

```text
zags/api/client.py             HTTP-клиент и пути запросов
zags/api/data.py               Синтетические данные для POST
zags/steps/api.py              Переиспользуемые действия и проверки
tests/conftest.py              Общие настройки из .env, флаг разрешения записи
tests/api/conftest.py          Сессии клиента и ID существующей заявки
tests/api/test_applications.py GET и параметризация авторизации
tests/api/test_admin_write.py  POST, который включают отдельно
```

Три уровня: тест задает сценарий и ожидания; шаг выполняет действие или assert; клиент знает HTTP.
Сессия Requests создается фикстурой и закрывается после теста. У каждого запроса есть timeout.
Пароль берется из `.env`, передается Basic Auth и не зашивается в URL. TLS проверяется.

Клиент возвращает `requests.Response`. Он не требует успешного статуса автоматически:
это позволяет тем же клиентом проверять и ожидаемый 200, и ожидаемый 401.
Сначала проверяем статус, затем Content-Type, JSON и нужные поля. Умение декодировать JSON
само по себе не означает успешный HTTP-ответ.

## Что показывают готовые примеры

1. `GET /getApplications`: ожидаем 200 и JSON-объект с `data` как списком; у записей есть
   положительный целочисленный `applicationid`. Пустой список здесь допустим.
2. `GET /getApplStatus/{applicationId}`: фикстура получает настоящий ID из списка, затем тест
   проверяет 200, JSON и поля статуса. ID не зашит в код и не берется из предыдущего теста.
3. Тот же запрос списка без Basic Auth и с неправильными доступами: два набора одной фикстуры,
   ожидаем 401. Тело такого отказа может быть HTML, поэтому JSON здесь не читаем.

Позитивные тесты повторно используют `api_client`, негативные — `unauthorized_api_client`.
Все действия и проверки импортируются из `zags.steps.api`, как наши UI-шаги.

## Сверка со стендом 29 октября 2026

Swagger прочитан с живого `https://regoffice.senla.eu/swagger/`. Он описывает 200 для GET
и для POST создания администратора, но не полностью соответствует фактическим телам ответов:

- `/getApplications` вернул объект с `total` (строка), `data` (список), `requestId` (строка).
- `/getApplStatus/{id}` вернул объект с `data` (объект) и `requestId`. В `data` находятся
  `dateofapplication`, `kindofapplication`, `statusofapplication` как строки. Поля `applicationid` там нет.
- Без авторизации и с неверными доступами `/getApplications` ответил 401. Это наблюдение стенда,
  а не описание негативных ответов в Swagger.
- Параметры `limit` и `offset` работают на стенде, но не описаны в прочитанной спецификации.
  Проверки пагинации в домашке рассматриваем как учебные ожидания, которые нужно сверить вручную
  и зафиксировать в PR, а не как восстановленные требования продукта.

Примеры JSON-структур поэтому основаны на явно отмеченном наблюдении. Они не объявляют
все расхождения дефектами и не являются полной проверкой Swagger-схемы. Для статуса не зашито
«На рассмотрении»: общая заявка могла быть обработана администратором.

## Необязательный POST с записью

`test_create_admin_returns_id` показывает `json=payload`, фабрику данных и проверку ID.
Ожидаемые 200 и положительный `staffid` взяты из Swagger `createAdminResp`. Успешный POST
на живом стенде при подготовке примеров не подтверждался; этот пример нужно проверять отдельно.
Сериализация HTTP-запроса и выполнение assertion проверены локально.

После согласования создания тестовой записи запускать только конкретный тест:

```powershell
pytest tests/api/test_admin_write.py -m api_write --allow-api-writes -v
```

Без `--allow-api-writes` тест пропускается даже при выборе маркера `api`. Он создает одного
синтетического администратора на запуск; удаления в описанном API нет. Не запускать его циклом.
Если фактический ответ отличается от контракта, сохранить разницу и обсудить ее, а не принимать
одновременно несколько альтернативных тел ради Passed.

## Allure и диагностика

Отчет содержит названия шагов, HTTP-метод, путь, статус и Content-Type. Полные тела заявок,
заголовок Authorization и пароль автоматически не прикладываются. При необходимости изучить
ответ локально и приложить только нужные обезличенные поля.

HTML вместо ожидаемого JSON часто означает, что сначала нужно разобраться с доступом, VPN
или адресом. Не маскировать это `try/except: pass`, ретраями или произвольным `xfail`.
В этой версии Allure в названии шага не используются необязательные `{limit}` и `{offset}`:
вызов с опущенными аргументами способен вызвать KeyError при форматировании. На этот случай
добавлена локальная регрессионная проверка; переданные параметры видны в данных шага.

## Как добавить свой сценарий

1. Сформулировать цель и источник ожидаемого результата.
2. Использовать готовый клиент и шаги; не создавать Requests-сессию внутри каждого теста.
3. Передать данные из теста, сохранить assertions в проверочных шагах.
4. Параметризовать одинаковые действия с разными входными данными.
5. Запустить только новый файл, проверить Allure и затем локальные проверки.

Не стоит фиксировать общее число заявок, конкретный существующий ID или постоянный статус
общей записи: такие ожидания зависят от чужой работы на стенде.

## Методы Allure в примерах

В `tests/api/test_applications.py` и `test_admin_write.py` показано оформление
непосредственно в тесте, а в `zags/steps/api.py` — оформление переиспользуемых функций.

| Метод | Где и для чего |
|---|---|
| `@allure.title` | Читаемое название; `{param_id}` у параметризованной авторизации |
| `@allure.description` | Цель, источник ожиданий и ограничения примера |
| `@allure.epic`, `feature`, `story` | Группировка по функциональности |
| `@allure.parent_suite`, `suite` | Группировка API-набора |
| `@allure.severity` | Важность проверки; не превращает Failed в другой статус |
| `@allure.link` | Ссылка на Swagger |
| `@allure.step` | Импортируемые действия и проверки в модуле шагов |
| `with allure.step(...)` | Общий блок проверки ответа или подготовки данных |
| `allure.dynamic.title(...)` | Название с ID, полученным во время выполнения |
| `allure.dynamic.parameter(...)` | Явный параметр выбранной заявки |
| `allure.attach(..., JSON)` | Сводка ответа и метаданные HTTP |

`with allure.step` группирует несколько действий по смыслу, а не дублирует каждый
уже декорированный вызов. Вложения сводки не содержат полный список записей и креды.
Смотреть эти примеры вместе с отчетом: метки видны в карточке теста, шаги — в Test body,
подготовка ID — в фикстурах, JSON — во вложениях.
