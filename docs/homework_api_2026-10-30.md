# Домашняя работа по API автотестам к пятнице 30 октября

Цель — самостоятельно написать небольшие API-проверки в нашем общем Python-проекте,
используя клиент, фикстуры, шаги, параметризацию и Allure. Ориентир по объему — 2–3 часа.
Если блокер по Git мешает старту, сначала разобрать его, не переносить весь проект в новый репозиторий.

## Подготовка

1. Сохранить текущую работу и корректно подтянуть `origin/main` в свою ветку.
2. Обновить зависимости через `pip install -e ".[dev]"`, проверить `.env` и VPN.
3. Запустить готовые API-примеры. Они выполняют четыре проверки без создания записей:

```powershell
pytest tests/api -m api -v --alluredir=allure-results --clean-alluredir
```

4. Пройти по цепочке `test → zags.steps.api → zags.api.client`, понять, где отправка, где данные
   и где ожидаемый результат. Прочитать [инструкцию](api_examples.md).

## Обязательная часть — три своих тестовых случая

Роман добавляет тесты в `tests/api/test_roman_applications.py`, Даниил —
в `tests/api/test_daniil_applications.py`. Не заменять готовый `test_applications.py`.
В обоих файлах задать `pytestmark = pytest.mark.api`. Все новые сценарии разметить для Allure.

### 1. Пагинация — одна функция, два набора

Проверить `GET /getApplications` с `limit=1` и `limit=3`, `offset=0`.
Использовать `pytest.mark.parametrize` с понятными `ids`.

Для каждого набора проверить HTTP 200, JSON, список `data`, корректность ID и условие
`len(data) <= limit`. Не требовать ровно limit записей: их может быть меньше.
Для дополнительной проверки поведения limit использовать значение total и наличие данных,
но не фиксировать конкретное общее число заявок.

Это согласованное учебное ожидание для наблюдаемого поведения: параметры не описаны
в текущем Swagger. Сначала проверить их руками в Postman и в PR указать источник ожидания.
Если данные есть, но лимит явно игнорируется, зафиксировать факт и обсудить, а не ослаблять assert.

### 2. Список и чтение одной заявки — один сценарий

Получить одну заявку из списка. Взять ее `applicationid` и `kindofapplication`.
По этому ID вызвать `GET /getApplStatus/{id}`. Проверить HTTP 200, структуру JSON и
совпадение типа заявки `kindofapplication` в обоих ответах. Ожидание передается из первой
выбранной записи; ручной ID не нужен.

Статус `statusofapplication` не сравнивать между двумя запросами: на общем стенде его
может изменить администратор. Если список пуст, явно пропустить этот сценарий с причиной.
Не создавать заявку скрыто в фикстуре ради чтения.

Для проверки размера страницы и совпадения поля добавить при необходимости свои
параметризуемые проверочные шаги. Общие готовые шаги повторно использовать. Перед
одновременной правкой общего файла договориться между собой, кто его меняет; можно
вынести новые шаги каждого в отдельный небольшой модуль. Логику HTTP не дублировать.

## Что сдавать

- PR из своей ветки: новый файл тестов и необходимые новые шаги. Готовые примеры не считаются
  тремя своими случаями.
- Команду запуска своего файла, итог passed/failed/skipped и скриншот Allure с раскрытыми шагами.
- Кратко описать, откуда взяты ожидания, как выбран ID и почему статус не зашит в код.
- Если есть сбой: точный traceback, какой шаг упал и что проверено самостоятельно.

Проверить `ruff check .` и `pytest`. Отчеты, `.env` и `.venv` не коммитить.
На созвоне каждый должен объяснить свой тест и прочитать отчет напарника. Можно помогать
друг другу; важно, чтобы оба понимали подготовку данных и каждую проверку.

## Дополнительно, если обязательная часть готова

`params=` и `json=`, зачем синтетические данные и почему запись защищена отдельным флагом.
